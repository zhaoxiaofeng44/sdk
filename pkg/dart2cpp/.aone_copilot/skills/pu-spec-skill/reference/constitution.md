## 文档目的

本文档定义 PuSpec（Process Unit Specification）体系的核心执行规则，确保 AI 准确理解并遵守所有强制规范。

**与 SKILL.md 的关系**：
- **SKILL.md**：面向用户的快速入门和核心概念（简洁版）
- **constitution.md**：面向 AI 的完整执行规范（详细版）

---

## A. 核心概念

### A.1 PU + SDD 定义

**PU（Process Unit，处理单元） + SDD（Specification-Driven Development，规范驱动开发）**：以详细规范文档为核心驱动力的开发模式。

**核心要素**：
- **PU**：单一职责的业务处理单元，对应独立接口/服务方法
- **规范文档**：`pu-xxx.json`（结构化定义）、`pu-xxx.impl.md`（实现设计）、`pu-xxx.detail.md`（技术方案）
- **核心目标**：可复现性、可测试性、可维护性

---

### A.2 文档标准

**业务语义**（MUST 满足）：
1. 业务目标明确（1-3 句话描述"做什么"、"为什么做"、"解决什么问题"）
2. 输入输出清晰（明确所有参数的类型、约束、含义）
3. 业务规则完整（列举所有规则、分支、异常）
4. 场景覆盖全面（正常/异常/边界情况）

**结构化规范**：
- 模板驱动：遵循 `impl.template.md` 结构
- 层次清晰：使用标准 Markdown 标题层级（# ## ### ####）
- 命名规范：ID 用 kebab-case，参数用 camelCase
- 约束明确：使用 MUST/SHOULD/MAY（RFC 2119）

---

### A.3 上下文管理

**分层加载策略**：

| Layer | 文档 | 加载时机 | 路径 |
|-------|------|---------|------|
| **0** | `constitution.md` | 所有任务前 | Skill 目录 |
| **1** | `project.md` | 所有任务前 + 生成代码前 | `{项目根目录}/puspec/project.md` |
| **2** | `knowledges/*.md` | 按需扫描 | `{项目根目录}/puspec/knowledges/` |
| **3** | `pu-xxx-change.json/detail.md` + `pu.sodd.md` | 执行变更指令时 | `{项目根目录}/puspec/changes/` |
| **4** | `pu-xxx.json/impl.md` + 代码片段 | 升级现有 PU 时 | `{项目根目录}/puspec/specs/` |

**说明**：
- `{项目根目录}` 指用户实际项目的根目录（非 Skill 目录）
- 所有项目特定文件统一存放在 `puspec/` 目录下
- Skill 目录保持纯净，仅包含规范文件

## B. 流程规范

### B.1 指令格式

**基础指令：**
```
init                    # 项目初始化
```

**PU 相关指令：**
```
impl ${pu_id}          # 生成实现文档
coding ${pu_id}        # 生成实现代码
ut ${pu_id}            # 生成单元测试代码
archive ${pu_id}       # 归档变更
```

**说明：**
- `${pu_id}` 为 PU 的唯一标识
- 指令与参数之间使用空格分隔

---

### B.2 核心执行原则

🔴 **防幻觉约束**（适用于所有指令）：
- ✅ **基于实际代码**：所有描述必须基于真实代码分析，不得假设或推测
- ❌ **禁止期望功能**：不得将 `pu-xxx-change.json` 中的期望功能写入基线文档
- ✅ **明确区分**：清晰区分"已实现"和"待实现"
- ✅ **验证机制**：通过 file_grep、codebase_search、read_file 验证功能存在性

🔴 **文档权威性**（适用于 coding 指令）：
1. 🔴 **变更实现文档**（`pu-xxx-change.impl.md`）—— 唯一执行准则
   - 100% 严格遵循其设计思路与实现方案
   - 禁止修改方法签名、增删参数、改变数据来源、改变逻辑顺序
   - 禁止简化/省略文档要求的步骤
   - 逐字逐句理解伪代码，严格按数据流转图实现

🔴 **增量更新策略**（适用于 impl/archive 指令）：
- ✅ 优先复用现有基线文档
- ✅ 仅更新有变更的相关章节
- ✅ 清晰标记更新 `[Updated YYYY-MM-DD]`
- ❌ 禁止全量重写基线文档
- ❌ 禁止假设代码与文档一致

🔴 **设计细节锁定规范**（适用于 impl 指令，detail.md 存在时 MUST 执行）：
**执行步骤**：
1. **提取关键设计点**（从 detail.md 中）：
   - 判断条件（如何判断、基于什么字段/属性）
   - 数据来源（从哪获取、如何获取、什么时机获取）
   - 处理逻辑（执行顺序、分支条件、循环边界）
   - 异常处理（什么异常、如何捕获、如何处理）
   - 技术选型（用什么库/工具类、什么算法/方法）

2. **逐项对照确认**（写入 impl.md 时）：
   - impl.md 中逐项体现上述每个设计点
   - 使用与 detail.md 完全一致的技术方案
   - 禁止任何"优化"、"简化"、"等价替换"

🔴 **导入验证约束**（适用于创建新文件）：
**强制规则**：
1. 对所有非 JDK 标准库的导入类，必须通过 `search_file` + `read_file` 验证完整包路径
2. ❌ 禁止凭类名、经验或相似类推测包路径
3. 异常类、结果码类、常量类等基础设施类优先验证

**操作流程**：
- Step 1: `search_file("<ClassName>.java")` 查找文件位置
- Step 2: `read_file` 确认 package 语句
- Step 3: 写入正确的 import 语句

**典型错误**：看到 `XxxException` 在 `common.exception`，推测 `XxxResultCode` 也在此包（实际可能在其他包）

### B.4 新建 vs 升级决策树

🔴 **关键警告**：决策错误导致严重问题（误判新建→缺乏参考；误判升级→浪费时间）

**执行流程**（不得跳过任何步骤）：

```
Step 1: 检查 {项目根目录}/puspec/specs/uc-xxx/pu-xxx/pu-xxx.json 或者 {项目根目录}/puspec/specs/uc-xxx/pu-xxx/pu-xxx.impl.md
├─ 任意一个存在 → 【现有 PU 升级】
└─ 不存在 → Step 2

Step 2: 全局搜索方法名
├─ 提取方法名/接口名：
│  ├─ 优先从 pu-xxx-change.detail.md 提取（如存在）
│  └─ 或从 pu-xxx-change.json 提取（如存在）
├─ 使用 file_grep/codebase_search 搜索所有 .java 文件
├─ 找到匹配？
│  ├─ YES → Step 3（二次验证）
│  └─ NO → 【新建 PU】
└─ 搜索失败？→ 询问用户确认

Step 3: 二次验证（防误判）
├─ 验证功能一致性
├─ 验证模块一致性  
├─ 验证业务逻辑匹配
└─ 通过 ≥2 项 → 【现有方法升级】
    通过 <2 项 → 【新建 PU】
```

**决策结果声明**（MUST 明确告知用户）：
- "经过验证，当前场景为：**【新建 PU】**"
- "经过验证，当前场景为：**【现有 PU 升级】**，基线文档：`{项目根目录}/puspec/specs/uc-xxx/pu-xxx/pu-xxx.impl.md`"
- "经过验证，当前场景为：**【现有方法升级】**，实现位于：`xxx/yyy/zzz.java`"

### B.5 深度嵌套细节追踪分析

**定义**：生成实现文档时，对代码进行深度分析，追踪方法调用链、分支路径、数据流转。

**三大分析策略**：

**1. 渐进式深度分析**
- 入口方法 (Depth 0) → 直接调用 (Depth 1) → 间接调用 (Depth 2) → 深层调用 (Depth 3+)
- 追踪至：外部依赖（DB/API）、工具类方法、递归终止条件
- 深度要求：MUST ≥3、SHOULD ≥5、MAY ≥7（复杂业务）

**2. 穷尽式分支分析**
- MUST 列举：所有 if/else、switch/case 分支
- MUST 列举：所有异常处理路径
- SHOULD 列举：所有循环边界情况

**3. 嵌套调用追踪**
- MUST 展开：领域内服务方法实现
- SHOULD 展开：工具类核心逻辑
- MAY 展开：第三方库关键方法

## C. 规则冲突与优先级

### C.1 文档优先级（从高到低）

1. 🔴 **技术方案设计文件**（`{项目根目录}/puspec/changes/uc-xxx/pu-xxx/pu-xxx-change.detail.md`）
   - 100% 遵循其技术决策、架构设计、实现方案
   - 不得偏离或质疑

2. 🔴 **变更实现文档**（`{项目根目录}/puspec/changes/uc-xxx/pu-xxx/pu-xxx-change.impl.md`）
   - 已在 B.2 核心执行原则中详细定义

3. **宪法文件**（`constitution.md`，Skill 目录）

4. **项目规范**（`{项目根目录}/puspec/project.md`）

5. **通用指令**（`custom_instructions`）
