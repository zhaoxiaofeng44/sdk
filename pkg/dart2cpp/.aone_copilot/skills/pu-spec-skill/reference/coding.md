#### 3. `coding ${pu_id}` - 生成实现代码

**触发时机**：实现文档审核通过后

**执行流程**：

---

**Step 1：生成编码计划**

> 📌 coding 前必须先生成任务规划，确保实现有据可循、进度可追踪

🔴 **读取文档**：
- `{项目根目录}/puspec/changes/uc-xxx/pu-xxx/pu-xxx-change.impl.md`（实现文档）
- `{项目根目录}/puspec/project.md`（编码规范）
- `{项目根目录}/puspec/knowledges/*.md`（领域知识）

**生成计划文件**：`{项目根目录}/puspec/changes/uc-xxx/pu-xxx/pu-xxx-coding-plan.md`

**计划表格模板**：
```markdown
# Coding Plan: pu-xxx

| 序号 | 功能点 | 涉及文件 | 参考实现 | 约束来源 | 复杂度 | 状态 |
|-----|-------|---------|---------|---------|-------|------|
| 1 | [功能描述] | `XxxService`(新增) | impl.md#3.1 / 代码库:YyyService | project.md#异常处理 | 中 | ⏳ |
| 2 | [功能描述] | `XxxEntity`(更新) | 业界:DDD聚合根模式 | knowledges/ddd.md | 简单 | ⏳ |
```

**字段说明**：
- **功能点**：对应 impl.md 中的功能点描述
- **涉及文件**：`类名`(新增/更新/删除)
- **参考实现**：`impl.md#章节` / `代码库:类名` / `业界:模式名`
- **约束来源**：`project.md#章节` / `knowledges/xxx.md`
- **复杂度**：简单 / 中 / 复杂
- **状态**：⏳待开始 / 🔄进行中 / ✅已完成 / ❌不通过

---

**Step 2：逐项执行编码**

🔴 **执行标准**：
1. 每次编码前读取 `impl.md` + `coding-plan.md`
2. 按计划表格顺序逐项实现
3. 🔴 **强制同步更新 plan.md**：每完成一个功能点的代码编写，**必须立即**更新 plan.md 中对应行的状态（⏳→✅）
4. 🔴 **100% 实现所有功能点**：禁止遗漏、简化、省略

🔴 **plan.md 更新规则**：
- 禁止使用其他任务管理工具（如 todo_write）替代 plan.md 的状态更新
- 每完成一个功能点后，立即使用 file_replace 更新对应行的状态
- 验证不通过时，更新状态为 ❌ 并记录失败原因
- 在 coding 任务结束前，必须验证 plan.md 中所有功能点状态都已更新为 ✅

**依赖管理**：
- 优先复用现有工具类和类库（先搜索代码库）
- 引入新依赖：检查 pom.xml → 评估必要性 → 选择稳定版本
- 🔴 **最小化影响**：优先添加到子模块 pom.xml，避免全局污染
- 明确告知用户新增依赖及其位置

---

**Step 3：验证与更新状态**

🔴 **验证流程**：
```
1. 代码验证通过后：
   - 更新 plan.md 对应行状态为 ✅
   
2. 验证不通过时：
   - 更新状态为 ❌
   - 记录失败原因
   - 修复后重新验证
   
3. 全部完成后：
   - 确认所有行状态为 ✅
   - 向用户报告完成情况
```

**编码质量标准**：
- **编码规范**（100% 遵循）：
  - 拒绝魔法数字、善用工具类、优雅 NPE、充血模型
  - 类 PascalCase、方法 camelCase、常量 UPPER_SNAKE_CASE
  - 缩进 4 空格、行宽 ≤120、方法 ≤50 行
  - 类/方法注释包含 `@author puSpec`
- **功能完整度**（100%）：对比 impl.md 逐项验证
- **架构一致性**（100%）：遵循项目分层架构

**代码生成后验证**（MUST 强制执行）：
1. 🔴 **静态分析验证**：使用 read_lints 工具验证代码，确保无编译错误、语法错误
2. 🔴 **零容忍标准**：不允许出现任何编译报错、类型错误等低级失误
3. ✅ 使用编码规范清单逐项验证
4. ✅ 向用户报告验证结果（必须通过所有检查）

**输出**：`主逻辑实现代码`

🔴 执行**B.2 核心执行原则**校验
